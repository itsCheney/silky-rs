The pop routine takes the script object in `ecx` and an output buffer on the stack.

Three things the spec does for this build:

- **Strings are UTF-8.** The engine turns the script's Shift-JIS text into UTF-8 when it pushes it, so the strings the probe reads from memory (`Voice.5` file names, the `Game.11` name) are UTF-8, and the spec says `"encoding": "utf-8"`. Read as Shift-JIS, `【小桃】` came out as `縲仙ｰ乗｡�縲�`.
- **`BackLog.3` has no arguments on the original side.** In the script its argument is a `push.cs` line of text, and that opcode does not push on the value stack: the text goes to the sink at 0x42cf20 and `BackLog.3` (handler 0x43c5ba) reads nothing. The spec reads the text at the sink (`hold`, a breakpoint that records no call but keeps its values) and gives it to the next `BackLog.3` (`carry`), so the call has the text as its argument, as in the runtime's trace.
- **Calls the engine runs itself are left out.** After the `MesWnd.3` of a line, the original records `Voice.5` and `Game.11` a second time with the same values, between `BackLog.3` and the next line, though the script has no statement there (`Voice.5` once per voiced line, `Game.11` once per line with a speaker). They go through the same `native` handler, run from the loop at 0x49f400, not from the script's own loop; the same happens in [engine-2026](engine-2026.md) (see there). `only` keeps the calls whose return address (read at `[[ebp]+4]`) is the script's own loop, 0x49ecaa. To check this on a run, take `only` out and add `"pc": "[[ebp]+4]"` to the breakpoint: the repeated calls should carry 0x49f46d, all the others 0x49ecaa.
